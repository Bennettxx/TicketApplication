Phase 1

Ausgangslage & Ziele

Das Problem

  • Support-Anfragen kommen unstrukturiert (Mail, Telefon, Zuruf) – gehen verloren.
  • Kein Status, keine Zuständigkeit, kein Verlauf.
  • Keine Datenbasis für Auswertungen (Wer? Wie lange? Welche Abteilung?).
  • Kunde erfährt nicht, was mit seiner Meldung passiert.

Ziel

Zentrale, nachvollziehbare Bearbeitung von Support-Tickets.

Nutzen

Transparenz, kürzere Bearbeitung, messbare Kennzahlen.

Ziele & Scope

In Scope
  • Tickets erstellen, bearbeiten, verfolgen
  • Rollen & Rechte (Admin/Support/User)
  • Chat, Zeiterfassung, Anhänge
  • Statistik & Wissensdatenbank
  • Lokaler Betrieb
Out of Scope (bewusst)
  • E-Mail-/SMTP-Versand → späterer Ausbau
  • KI-gestützte Lösungsfindung
  • Mehrmandantenfähigkeit
  • Mobile App

SMART-Ziele + klare Abgrenzung → kein „Scope Creep".

Phase 2

Anforderungen & Rollen

Rollen & Berechtigungen

User (Kunde)

Tickets erstellen, eigene sehen, chatten, Anhänge, Problemmeldung. Gehört einer Abteilung an.

Support

Alle Tickets bearbeiten: Status, Zuweisung, Zeiterfassung, interne Notizen, Wissensdatenbank.

Admin

Alles wie Support + Benutzerverwaltung, Statistik, Problemmeldungen.

Prinzip Least Privilege: jede Rolle nur so viel wie nötig.

Anforderungen als User Stories

  • „Als User möchte ich ein Ticket mit Priorität und Beschreibung erstellen, damit mein Problem erfasst wird."
  • „Als Support möchte ich Tickets auf einem Board verschieben, um den Fortschritt zu steuern."
  • „Als Support möchte ich Zeit pro Ticket erfassen, damit Aufwände messbar werden."
  • „Als Admin möchte ich Auswertungen pro Abteilung sehen, um Ressourcen zu planen."
  • „Als User möchte ich eine Antwort-Benachrichtigung, um nichts zu verpassen."
Phase 3

Projektvorgehen

Iteratives Vorgehen in Ausbaustufen

  • Stufe 1: Grundgerüst, Auth, Ticket-Basis
  • Stufe 2: Bearbeitung, Kanban, Chat, Zeit
  • Stufe 3: Anhänge, Dashboard, Suche, Wissens-DB

Warum iterativ?

  • Priorisierung über Backlog

Gesteuert visuell – per Kanban (To Do → In Arbeit → Erledigt).

  • Id (PK)
  • TicketId (FK)
  • verschlüsselt?

1 Ticket : n Nachrichten / Zeiteinträge / Anhänge — verknüpft über Fremdschlüssel.

Modellierungs-Grundlagen

  • Normalisierung: Abteilung/Thema als eigene Tabelle statt Freitext → keine Redundanz
  • PK/FK & referenzielle Integrität
  • Enums für feste Wertebereiche (Status, Priorität)
  • Indizes auf Fremdschlüsseln (z. B. TicketId)
  • Soft-Delete (IsActive) statt echtem Löschen
  • Audit-Tabelle (TicketTransaction) für Verlauf
// Fester Wertebereich statt "magischer" Zahlen/Strings
public enum TicketStatus { Open = 0, InProgress = 1, Closed = 2 }
Phase 6

Implementierung & Features

Backend – Aufbau

Model

Datenbank-Entität (z. B. Ticket, User). Von EF Core auf Tabellen abgebildet.

DTO

Datentransfer-Objekt: definiert exakt Ein- und Ausgabe der API. Trennt intern ↔ öffentlich.

Controller

REST-Endpunkte, Rollenprüfung, ruft EF Core auf. Dünn gehalten.

Beispiel: UserResponseDto enthält keinen Passwort-Hash → sensible Daten bleiben im Backend.

REST-Schnittstelle

GET    /api/ticket            // Liste (mit Suche & Filtern)
POST   /api/ticket            // neues Ticket (nur Rolle User)
PATCH  /api/ticket/{id}/status // Status ändern (Kanban)
POST   /api/ticket/{id}/reopen // wiedereröffnen (Pflicht-Nachricht)
GET    /api/statistics/departments // Auswertung
  • Verben = Aktion, Pfad = Ressource
  • Sprechende Statuscodes: 200/201, 400, 401/403, 404

Umgesetzte Kernfunktionen

Kanban-Board

Drag & Drop, Zeitraum-Modi (gesamt/60/30 Tage).

Ticket-Chat

Dialog + interne Notizen (nur Staff).

Zeiterfassung

Wissensdatenbank

Lösungsvorschläge schon beim Tippen des Titels.

Anhänge

Privat (verschlüsselt) oder öffentlich (Datei).

Problemmeldung

Auch anonym vor dem Login.

Benachrichtigung

Kennzeichnung bei neuer Antwort.

Statistik

Phase 7

Sicherheitskonzept

Authentifizierung – Wer bist du?

  • Passwörter mit BCrypt gehasht + gesalzen – nie Klartext
  • Login liefert ein signiertes JWT (Token)
  • Token bei jedem Request → zustandslos
  • Abgelehnte/gesperrte Konten mit klarer Meldung
// Passwort prüfen, nie entschlüsseln
bool ok = BCrypt.Verify(pw, user.Hash);
if (!ok) return Unauthorized();

Autorisierung – Was darfst du?

[Authorize(Roles = "Admin,Support")]
public IActionResult Bearbeiten() { ... }
  • Rolle steckt im JWT-Claim
  • Deklarativ pro Endpunkt geprüft
  • Zusätzlich feingranular im Code: „User sieht nur eigene Tickets"
  • Interne Notizen für Kunden serverseitig gefiltert
  • Least Privilege durchgezogen

Eingabevalidierung – „Eintrittstor"

public class CreateProblemDto {
    [Required][MinLength(3)][MaxLength(200)]
    public string Title { get; set; }
    [Required][EmailAddress]
    public string ContactEmail { get; set; }
}
  • Never trust user input – Prüfung vor jeder Logik
  • Ungültig → automatisch 400 Bad Request
  • Eigene Prüf-Attribute (z. B. „existiert in DB?")

Weitere Schutzmaßnahmen

Verschlüsselung

Private Anhänge mit AES-GCM verschlüsselt in der DB.

Secrets-Management

DB-String & Schlüssel in Prod aus Umgebungsvariablen – nie im Code/Repo.

Transport & CORS

HTTPS-Redirect, definierte CORS-Regel fürs Frontend.

Defense in Depth – mehrere Schutzschichten statt einer einzigen.

Phase 9

Betrieb, Reflexion & Ausblick

Betrieb & Konfiguration

Development
  • Lokale Konfig-Datei
  • Schlüssel werden automatisch erzeugt
Production
  • Alles über Umgebungsvariablen
  • Fehlt ein Secret → App startet nicht (fail fast)

Nachvollziehbar dokumentiert (Anleitung im Repo).

Herausforderungen & Lessons Learned

  • Anforderungen früh schärfen – Rückfragen sparen später Umbau (z. B. Rollen & Abteilungen).
  • Schema-Änderungen brauchen Disziplin – lokale DB-Neuerstellung als Stolperstein.
  • Validierung zentral halten (DTOs) spart verstreute Prüfungen.
  • Tooling verstehen – Browser-Cache kostete Zeit, bis Ursache klar war.
